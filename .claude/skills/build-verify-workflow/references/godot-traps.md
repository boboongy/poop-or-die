# GDScript / Godot 4.7 traps met so far

Read this when the symptom matches a heading word (types, lambdas, AnimationPlayer, freed objects, gates, headroom, navigation). (Moved out of SKILL.md on 2026-09-27.)

- **Types:** `:=` fails when the value is a Variant (dictionary lookups, arrays, `find_children`, untyped node access): write the type. Assigning an untyped array to a typed `Array[int]` through an untyped reference fails: use `.assign([...])`.
- **A lambda cannot reassign a captured local:** use a one-element array or a member (twice: a `pressed := false` flag set in a callback never changed outside it; a polling loop hung silently). Grep any new `:= func` that assigns an outer local.
- **AnimationPlayer:** (a) clips advance on the RENDER frame by default; when logic must match a clip frame set `callback_mode_process = ANIMATION_CALLBACK_MODE_PROCESS_PHYSICS` and restore it. (b) `speed_scale = 0` freezes the BLEND too: cut a tiny looping clip instead (`fight.gd` `_slice`). Only a screenshot at the contact moment shows either. Models face +Z, their right is -X; `player.posing` = another script owns Bob's AnimationPlayer.
- **Freed objects:** anything bound to a timer/signal callback or held across an `await` can be freed first: take it UNTYPED and check `is_instance_valid` (twice). Read the FINAL output of `stop_project` too.
- **Gates:** before bypassing a `busy`/`frozen`-style gate for a new state, grep every place that flag is checked (2026-09-23: `player.posing` skipping the scan let the stall door behind Bob become E-able). A narrow allow-list beats a blanket bypass.
- **Headroom:** anything that lifts a body off the floor (swim, float, jump) needs a headroom probe of the whole map first (the 2.1 m lintel over the waiting-room doorway; `tests/probe_flood_headroom.gd`). A lintel is thin: sample several points ahead.
- **Navigation:** check the baked mesh height, cell size vs the narrowest doorway, agent radius, then test every destination.
- **Missions:** a `const` declared in the mission base class must not be redeclared in a subclass (the mission silently fails to load).
- **One-shot particles made in code:** a new `CPUParticles3D` has `emitting = true`, so it fires at the origin before you place it and `finished` frees it unseen (2026-09-27, the shooter's splash: tests counted splashes, the screenshot showed none). Create with `emitting = false`, place, then `restart()`; check it with a frame-by-frame windowed shot (`tests/shot_shooter_splash.gd`). Also: a line-of-fire ray needs layer 2 (walkers) as well as 1.
- **Hiding a node does not take it out of its groups:** a walker with `visible = false` and processing off still offered "E talk" (the player scans the "interactable" group, not visibility). A mode that hides things must also take them out of the group and put them back after (2026-09-27, the shooter; my first fix cleared the WRONG nodes and only a sabotage run showed its check could not go red).
- **Web build speed: measure in a REAL browser, not native `--rendering-method gl_compatibility`** (2026-09-28: native said 31 FPS while Chrome gave 4; WebGL costs ~0.13 ms per DRAW CALL, so count draw calls (`Performance.RENDER_TOTAL_DRAW_CALLS_IN_FRAME`) and merge multi-mesh characters; resolution scale barely mattered). Compatibility depth is -1..1 in shaders; MSAA's depth blit fails in WebGL.
- **Web speed tools live in the repo:** `tools/web_fps.py` (real Chrome, per-level FPS + probe lines) and `tests/probe_compat_fps.gd` (native draw calls, `lights=noshadow`, `hide=NAME`). 2026-09-28: last session's browser script lived only in a scratchpad and was lost. One shadowed spot in Compatibility = ~220 extra draw calls (L3 500 -> 280 with no characters).
- **A web-only LOOK bug: native Compatibility does NOT reproduce WebGL** (2026-09-28, black flood water, 1 h+): at once capture Chrome's console `warning`s (WebGL errors: here "glBlitFramebuffer: Depth/stencil ... not allowed" = `hint_depth_texture` unusable) and bisect the shader with a few debug views (ALBEDO only, EMISSION only, ALPHA=1) in ONE build; measure pixels (ffmpeg crop+scale=1:1), do not eyeball. In the web build a transparent sheet also got NO lamp light: fake it in EMISSION (`flood_water_web.gdshader`).
- **"It halves at full screen": measure BOTH resolutions before believing it** (2026-10-10, owner's 20 -> 10 FPS at 1080p on an integrated Radeon; measured, 720p 23.6 -> 1080p 17.4, only 26 % for 2.25x the pixels, so the missing half was OBS's software x264, not the game): `liminal_lighting.gd` runs MSAA 4x (unconditional, line 58) + SSR + SSAO + volumetric fog + SDFGI + glow; only the web/compat path is cut down. Before touching a shader, list which settings scale with pixel count, and remember a laptop APU shares its power budget with the CPU (so OBS software x264, Balanced plan or a low battery halve it too: check `Get-Process obs64`, `powercfg /getactivescheme`, and the OBS log's "lagged frames" line). The desktop FPS probe is `tests/probe_fullscreen_fps.gd` (a real window, `res=`, `runs=`, every ladder setting as an argument, `--perf=` to force a tier); `tools/web_fps.py` is Chrome-only and the `shot_*` tests' single-frame FPS is meaningless. Never measure FPS under `--fixed-fps` or `--headless`, throw the first 90 frames away (shader compilation) and report a MEDIAN of several runs: run 3 of a baseline triple came in 8 FPS under runs 1-2. Plan + measured ladder: `PERF_PLAN.md`.
- **A ONE-AT-A-TIME performance ladder LIES on an integrated GPU** (2026-10-10, the whole PERF_PLAN ladder, ~1 h): at 1080p, MSAA off, SSR off, SSAO off, fog off and ALL 10 shadows off each changed the frame rate by under 1 FPS, yet switching the whole stack off gave 68 FPS against 17. The APU is memory-bandwidth bound, so removing one effect only lets the rest fill the gap, and each one measures "free". **Measure the stack OFF first to find the ceiling, then add effects BACK one at a time** (that is how shadows turned out to cost 19 FPS and SDFGI the rest). Draw calls proved nothing here: shadows off cut them 7000 -> 591 for +0.2 FPS. Also re-measure every candidate in the regime the game will ship in, never in the slow one.
- **A float read back from a Godot property is float32:** `vp.scaling_3d_scale == 0.8` is false after setting it to 0.8 (it reads 0.80000001). Use `is_equal_approx` in every test that checks a float property (2026-10-10, cost one red test).
- **A probe setting the game code puts back is a SILENT fake measurement** (2026-10-11, `probe_compat_fps.gd shadows=none` printed `shadowed 1` and "no change", because `liminal_lighting.gd:207-210` re-runs `_update_shadow_light()` every 0.25 s and switches the nearest spot back on): before believing a rung that measured "free", check that the probe's own print-back shows the setting still applied, and grep the scene's scripts for a timer or `_process` that owns that property. Related: a web FPS number without its viewport size is meaningless, but **for the web build the pixel count is NOT the variable** - native 1080p 46.8 vs Chrome 10.6 FPS on the same level and renderer (4.4x) is per-draw-call browser overhead (WASM -> JS -> ANGLE), so rank web rungs by the DRAW-CALL delta in a native probe and confirm only the winner in Chrome (`SIZE=1920x1080 python tools/web_fps.py`).
- Use `preload("res://...")` constants, not `class_name`, in test/headless scripts. Cross-scene state goes in a static var; `project.godot` is editor-owned, so no autoload.
