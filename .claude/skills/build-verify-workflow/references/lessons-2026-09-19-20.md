# Lessons: what went wrong on days 1-2, and why

Scope: the game work (levels, characters, stalls, poses, dialogue), NOT the water-video work (its own lessons are in the 3d-water-animation skill).
Cause classes: **Process** = the order of work or an unchecked assumption. **Missing context** = information that existed only in the owner's head or nowhere. **Weak rule** = a rule existed but was vague, buried or not enforced. **Unreliable tooling/code** = the mechanism kept failing.

## Totals
Process 8, weak rule 3 (one overlaps process), missing context 3 (partial), unreliable tooling/code 2.
The pattern: **the knowledge was mostly available, the order of work was wrong.** The cheap fixes are a checklist at the start, probing before building, testing all instances, invariants for state switches, and tests that survive the session.

## What worked (keep doing)
- Asking with AskUserQuestion options, recommendation first, and recording each answer in SPEC.md straight away.
- Headless tests driven by real key events (they caught navigation, prompt and sequencing bugs).
- Screenshots via a windowed script, contact sheets, and reading the debug output after every launch.
- Numeric fitting (scan arm angles against sink geometry) instead of nudging by eye.
- Saying plainly what was run, seen, and not verified.
- Recording asset needs in FACTORY_TODO.md as they were discovered.

## Limits of this file
It is a diagnosis by one session reading its own history. The tests in `tests/` were seen to pass, and the head test was seen to fail when its fix was broken on purpose; the other tests were not mutation-checked. Rules are advice: prefer making a rule mechanical when it is missed twice.
